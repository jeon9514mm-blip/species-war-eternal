# V27 밸런스 기준과 8개 영역 마감 판단

## 무엇을 완료로 판단하는가

사용자의 “95% 이상”은 아래 기능을 끝까지 구현하고 검증하라는 개발 목표로 해석한다.
자동화 검사 통과율을 개발 완성도로 바꾸지 않는다. 예를 들어 145개 검사가 통과해도 게임이 100% 완성되었다는 뜻은 아니다.
기존 20명 영웅, 2개 진영, 3개 사냥터, 최대 10인 파티의 로컬 게임 범위와 실제 서비스 운영 준비를 구분한다.

| 영역 | 현재 범위의 필수 완료 기준 | 별도 확인이 필요한 범위 |
|---|---|---|
| 실시간 자동사냥 / 전투 AI | 실제 이동과 공격 거리 일치, 사망한 영웅의 행동 차단, 유효 대상 재선택, 전멸 복귀, 반복 보상 차단, 10인 지속 사냥 진행 | Android 기기에서 장시간 발열·프레임·배터리 측정 |
| 영웅 스킬·개성·역할 | 20명 모두 고유 역할과 실전 효과 존재, 탱커 보호·지원 회복·제어·딜러 타격 검증, 공통 상태 효과 중복·지속시간 안전 | 모든 조합과 장비 등급에서 장시간 역할별 기여도 비교 |
| 성장·장비·방치 | 레벨·강화 상한, 실제 능력치 증가, XP 보존, 장비 교체와 세트 반영, 8시간 보상 상한·중복 수령 차단 | 수 주간 성장 속도·경제 소모와 획득량 추적 |
| 보스 / 레이드 | 세 보스 패턴과 위험 예고, 반응 가능 시간, 전멸·시간초과·승리 구분, 재시도와 보상 1회 처리 | 여러 플레이어가 연결된 실제 협동 레이드 |
| 필드 몬스터 / 전투 | 존별 적 구성·지원·원거리·암살 행동, 추격과 복귀, 처치 후 다시 생성, 전투 보상 연결 | 추가 맵·시간대·장기 생태계 콘텐츠 |
| 종의전쟁 / 영토전 | 현재 로컬 권위 서비스의 이동·도착·전투·소유권·주둔·보급·보상 흐름, 요청 재전송 안전 | 운영 서버 배포, 외부 클라이언트 동시 접속과 부하 검증 |
| 밸런스 기반 | 실제 게임 함수의 20명 능력치와 2진영·3존·3/10인 실측, 성장·방치 단조성, 범위 상한 | 대규모 조합 샘플·PvP 승률·장기 재화 경제 |
| 저장 / 안정성 / 회귀 | 버전 이전, 손상 파일 복구, 비정상 타입·숫자 처리, 저장 후 복원, 재접속 보상·권위 상태 보존, 통합 회귀 검사 | 모바일 OS 강제 종료·저장 공간 부족·실기기 장기 운용 |

이 표는 합격을 선언하는 문서가 아니다. 최종 통합 코드와 실행 결과가 각 항목의 근거다. 해당 결과가 없으면 미검증으로 남긴다.

## 재현 방법

Godot 4.7.2에서 프로젝트 리소스를 먼저 import한다.

```bash
godot --headless --editor --path . --import --quit
godot --headless --path . --script res://tests/regression/V27BalanceMatrixSmokeTest.gd -- --report=res://docs/v27-balance-results.json
python tools/balance_report.py docs/v27-balance-results.json docs/V27_BALANCE_RESULTS_KO.md
```

전체 회귀 실행기에도 스크립트가 자동 포함된다. 단조성 계약만 재확인할 때는 `--contracts-only`를 쓴다. 이 옵션은 실제 전투 매트릭스를 실행하지 않는다.
전체 실행은 900초의 게임 시간을 고정 0.1초씩 진행한다. 느린 머신이나 병렬 작업 중에는 실행 제한 시간을 600초로 설정한다.

측정 조건:

- 기본 12행: 2진영 × 3존 × 3/10인, 모든 영웅 Lv.10, 일반 장비 +3, 스테이지 25, 각 60초, 순찰·전리품 시드 2701.
- 경계 3행: 아우렐리아 3인, Lv.1, 일반 장비 +1, 같은 스테이지 25의 초원, 시드 2701·2713·2741. 신규 계정의 튜토리얼 진행 속도를 측정한 조건은 아니다.
- 10인에서 모든 영웅 20명의 실제 HP·공격·방어·공격 주기 배율을 기록한다.
- 각 행의 시작 상태는 독립적이다. 저장 입출력과 HUD 재그리기만 차단하며 실제 Main 전투·이동·스킬·적 생성·드롭·성장·보상 함수를 그대로 사용한다.
- 양 진영에 같은 순찰과 전리품 시드를 주고, 각 행 안에서 발생하는 XP·드롭 성장도 그대로 진행한다. 그러므로 고정된 DPS 시험 대신 짧은 실제 게임 루프 비교다.
- `encounters_cleared`는 적 무리의 전멸 횟수다. 개별 적 처치 수와 혼용하지 않는다.

## 허용 기준

| 검사 | 기준 | 목적 |
|---|---|---|
| 체력·사망 상태 | 매 시점 0 ≤ HP ≤ 최대 HP, alive와 HP 일치, 파티 합계 일치 | 숫자 손상과 죽은 영웅의 잘못된 상태 탐지 |
| 실제 사냥 진행 | 모든 측정 행에서 60초 안에 적 무리 최소 1회 격파 | 기능 정지 감지 |
| 진영 처리량 | 같은 인원·존에서 한 진영이 다른 진영의 2배를 넘지 않음 | 거대한 우위나 동작 누락을 잡는 넓은 회귀 기준 |
| 10인 진영 능력치 | 실제 HP·공격 합·표시 전투력 각각 차이 10% 이내 | 카탈로그 가중치만 검사하는 문제 보완 |
| 성장 | Lv.1→10→50→100에서 실제 HP·공격 합·전투력 엄격 증가 | 표시 수치만 성장하는 오류 탐지 |
| 장비 비용 | +1부터 +10까지 비용 증가 | 강화 가격 역전 탐지 |
| 존 성장 | 동일 인원으로 생성한 무리 총 HP와 기본 골드가 초원→광산→숲 순으로 증가 | 적 난이도와 보상 표의 연결 확인 |
| 방치 단조성 | 같은 존에서 전투력·인원·시간 증가가 골드·처치 수를 감소시키지 않음 | 계산 경계의 역전 탐지 |
| 극단값 안전 | 레벨·장비·방치 시간·스테이지·비정상 숫자 상한 | 성장·안정성 전용 회귀에서 별도 검증 |

2배 처리량 기준은 경쟁 밸런스 목표가 아니다. 최종 조정 목표를 정하려면 더 긴 표본과 조합별 생존·치유·제어 기여도를 수집해야 한다.
60초에서는 1회 격파 차이만으로 비율이 크게 달라질 수 있으므로 방치/온라인 골드 비율은 보고만 하며 단일 표본으로 자동 너프하지 않는다.

## 통합 이전 기준선

`v27-balance-baseline.json`과 `V27_BALANCE_BASELINE_KO.md`는 V26 기준 커밋 `ce8bdc15aa746f41d73369aff69a277d5e124f8e`에서 측정했다.
15개 행의 체력과 진행 검사가 통과했다. 이 데이터는 V27 변경 후의 결과로 제시하면 안 된다.

| 조건 | 아우렐리아 무리/60초 | 녹스페라 무리/60초 |
|---|---:|---:|
| 초원 3인 | 20 | 22 |
| 초원 10인 | 20 | 20 |
| 광산 3인 | 12 | 13 |
| 광산 10인 | 13 | 14 |
| 숲 3인 | 9 | 12 |
| 숲 10인 | 9 | 10 |

10인 실제 HP는 12,598 / 12,611, 공격 합은 1,116 / 1,121, 전투력은 9,181 / 9,235였다.
3인 시작 조합은 탱커·치유를 가진 아우렐리아와 흡혈·공격 비중이 높은 녹스페라의 구성이 달라 같은 능력치 예산이 같은 처리량을 뜻하지 않는다.
이 표본에서 녹스페라 3인 숲 처리량이 33% 많다. 패시브 예산 차이가 3% 이내라는 기존 검사만으로 실전 격차를 설명할 수 없다.

방치/온라인 골드 비율은 기본 12개 조건에서 0.341~1.040이었다.
아우렐리아 10인 숲은 방치 추정 1,320골드, 온라인 1,269골드로 4% 차이가 났다.
방치 계산의 상수 0.88은 추정 처치 수에 적용되는 계수다. “온라인 수익의 정확히 88%”라는 설명은 근거가 없다.
최종 통합 결과에서도 큰 차이가 지속되면 존별 실제 처치 시간과 재정비 빈도를 더 수집한 뒤 보정한다.

## 감사에서 발견해 통합 담당에 전달한 안전 문제

V26에서 0 또는 음수 피해가 최소 1 피해로 변환되고, 취약 배율에 극단적인 정수를 곱하면 정수 범위를 벗어날 수 있었다.
받은 피해 반환값도 현재 HP를 넘는 과잉 피해를 포함했다. 전투 경계에서 거부·상한·실제 감소량을 처리하도록 전투 담당에게 전달했다.
성장 레벨과 XP 반복 처리, 입력 스테이지의 전투력 기여, 방치 계산기의 외부 입력 상한도 성장·저장 담당의 경계 검사와 함께 보완 대상으로 전달했다.
이 항목들은 최종 통합 코드와 해당 회귀 테스트의 성공 여부로 해결을 확인한다.

밸런스를 측정하기 전에 임의의 새 수식이나 사용하지 않는 BalanceRules 모듈을 추가하지 않았다. 현재 수치의 근거와 회귀 기준을 먼저 남기는 것이 이후 조정에 필요하다.
